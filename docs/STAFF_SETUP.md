# Enable administrator access, staff accounts and private uploads

Use the existing [Loud + Cana service in Render](https://dashboard.render.com/web/srv-dbd567t9fdbs73agdiq0). No second service or third-party identity-verification account is needed. The full application is **https://loud-cana.onrender.com/**; GitHub Pages is a separate public catalog snapshot.

The latest public check reports a healthy live service and configured encrypted ID storage. Preserve the existing valid upload key, administrator secret and database settings when deploying these changes. The setup steps below also apply to a new host. Welcome emails require the separate sender setup in [EMAIL_SETUP.md](EMAIL_SETUP.md).

## 1. Confirm persistent storage

Before registering real members or accepting identity photographs, open the service's **Disks** settings and confirm that a persistent disk is mounted at **`/var/data`**. In **Environment**, set **`DATABASE_PATH`** to **`/var/data/orders.sqlite`**. This must be a disk-backed path, not just an environment variable pointing at an ephemeral directory.

The prepared Blueprint uses a paid Starter service and a persistent disk. The existing service's disk has not been verified through its public API. Check the actual service and any cost shown in Render before changing its plan or adding a disk. If existing data is stored elsewhere, back it up and migrate it deliberately before changing `DATABASE_PATH`; changing the path alone creates an empty database at the new location.

The database holds member accounts, employee accounts, products, reviews and encrypted pending identity photographs. Maintain restricted, tested backups.

## 2. Set the administrator password

1. In the existing Render service, open **Environment → Edit** or **Add Environment Variable**.
2. Add **`ADMIN_PASSWORD`** if it is missing, or perform a planned reset of its existing value. Use a unique password generated by a password manager: at least **16 characters**, preferably 20 or more.
3. Save the password in the owner's password manager. Keep it out of this chat, source files, GitHub, the client ZIP and screenshots.

The administrator's sign-in username is **`admin`**. This environment password is the administrator credential; employees will receive their own accounts in step 5.

## 3. Set the upload-encryption key once

If **`IDENTITY_UPLOAD_KEY`** is already configured and has accepted uploads, preserve that exact value. Do not replace it merely because code is redeployed. Changing or losing the key prevents decryption of existing pending photographs.

For a new installation, generate a random key on the owner's computer. On macOS or Linux, open Terminal and run:

```sh
openssl rand -hex 32
```

On Windows, the equivalent PowerShell command is:

```powershell
$keyBytes = New-Object byte[] 32
$keyGenerator = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$keyGenerator.GetBytes($keyBytes)
($keyBytes | ForEach-Object { $_.ToString("x2") }) -join ""
$keyGenerator.Dispose()
```

The result must be exactly **64 hexadecimal characters**, with no spaces or quotation marks. These commands generate a new private value; no example key from documentation should be reused.

In Render **Environment**, add **`IDENTITY_UPLOAD_KEY`** and paste that result as its value. Store a secure backup separately from the database. Do not send the value to the developer or paste it in chat, source, build commands or build logs. Without a valid key, uploads are rejected and applications stay unverified.

## 4. Save and deploy

Save the Environment changes and choose Render's rebuild/deploy option. If necessary, use **Manual Deploy → Deploy latest commit** after saving. Wait until deployment reports success, then open **https://loud-cana.onrender.com/api/health** and confirm it returns `"ok": true`.

Open **https://loud-cana.onrender.com/login**. Enter **`admin`** in **Email or username** and the `ADMIN_PASSWORD` value in **Password**. Successful authentication opens **`/admin`**.

You do **not** need to set a shared `STAFF_PASSWORD` for the individual employee accounts below. Leave that optional legacy variable blank, or remove it after migrating any old shared-login users. A deployment after removal ends the old shared login. Never reuse the administrator password for an employee.

## 5. Create individual staff accounts

1. From the admin dashboard, open **Staff accounts** and select **Create staff account**.
2. Enter the employee's name, a unique username and an initial password. Usernames use 3–40 characters, start with a letter, and contain only letters, numbers, dots, underscores or hyphens. `admin` and `staff` are reserved. Employee usernames are not email addresses.
3. Use a unique password of **16–256 characters** and select **Create account**. Store or deliver it through the business's approved private channel. The application stores a salted hash and does not later display the saved password.
4. The employee opens the same **`/login`** page and enters their assigned username and password. Successful authentication opens **`/staff`**.

Employees can review applications and use the operational member, product and order tools. Only the administrator can create or manage staff accounts or open the administrator Overview. Public navigation has no staff-access link; sign-in and server-side permissions determine access to the private workspaces.

## 6. Review member applications from the staff dashboard

1. Sign in using the employee's own username and password. Select **Review applications** or the **Age checks** tab.
2. Open the current pending member application. View both the private ID photograph and selfie, compare the photographs, and compare the ID name and birth date with the application. Confirm that the document shows an age of at least **18**. If evidence is missing, unreadable or uncertain, do not approve it.
3. After actually performing the comparison, select both required identity-comparison and adult-age attestations. Choose **Verify 18+ ID check**, then confirm the decision. Otherwise use the structured rejection flow and its appropriate reason.
4. Refresh if the member replaced the upload or another reviewer acted; the server rejects stale decisions. Reviewed photographs are removed from active storage after approval or rejection. Pending photographs expire after seven days; backup retention is a separate owner duty.

This is a human comparison of submitted photographs. It does not provide automated face matching, document-authenticity checking or liveness detection. A questionnaire, successful upload or checkbox alone never verifies a member. Read [the identity review guide](IDENTITY_VERIFICATION.md) and [South African operating guide](SOUTH_AFRICAN_SIGNUP.md) before reviewing real people.

## 7. Reset or revoke staff access

In **Admin → Staff accounts**, find the employee. **Reset password** lets the administrator enter a replacement and confirm **Reset password and end sessions**. **Disable access** blocks login and invalidates that employee's existing sessions; **Enable access** permits login again. Changing an employee username also invalidates its earlier sessions. Restrict these controls to the administrator and review access when employment changes.

Welcome messages for member signups do not provide staff invitations or password-reset email. Use the business's approved private credential-delivery process for employee accounts; do not tell an employee to expect an automatic invitation or recovery message.

## 8. Delete a registered member

1. Sign in as the administrator and open **Members**. Staff can review applications but cannot delete accounts.
2. Find the exact account and choose **Delete member**. Read the displayed consequences, type that member's email and confirm **Delete member permanently**.
3. If the account changed since it was displayed, refresh the directory and review it again. The server checks the displayed account version as well as the typed email, so a stale confirmation cannot silently delete a changed profile.

Deletion removes the member profile, favourites, sessions, linked ID/age-check records and unsent welcome-email jobs. Existing orders remain and are not cancelled. Already delivered or in-flight email cannot be recalled; historical backups have their own deletion schedule. This closes the current account and does not ban a future fresh signup. Use an isolated local fixture rather than a real customer for acceptance testing.

## 9. Upload a product photograph

1. Open **Products**, create a draft or edit an existing product, then select **Product photo**.
2. Choose a static **JPEG, PNG or WebP** of at most **6 MiB**. It must be at least **64 × 64 pixels** and no more than **20 megapixels**. Use a product photograph the business has permission to publish; do not put identity evidence in the product editor.
3. Select **Upload photo** and wait for a successful preview. The server strips metadata and stores a WebP limited to 1,600 pixels per side. A selected file is not saved merely because it appears in the browser; complete the upload and save the product.
4. Save the draft, then publish when the actual product details, photo, price and stock are approved. Draft image previews require staff access. The public image works only while a published product references it; archiving removes that public availability.

The photo and product persist in SQLite. Unreferenced uploads expire after 24 hours; saved product references protect their images. The optional direct HTTPS image URL remains available. Changes update the full Render storefront; Pages and offline copies need a fresh export/publication to change their bundled snapshot.

## 10. Enable and monitor welcome emails

Set `CONTACT_EMAIL` and `EMAIL_REPLY_TO` to **`loudpluscana@protonmail.com`** in the existing Render service's private Environment settings, preserving the administrator password, identity-upload key and persistent database settings. This sets the public contact and reply address; it does not authorise automatic sending.

Follow [EMAIL_SETUP.md](EMAIL_SETUP.md) for the complete Proton steps. [Proton's direct SMTP service](https://proton.me/support/smtp-submission) requires a paid Proton Mail plan and an active **custom-domain** address. The `@protonmail.com` mailbox cannot use this direct SMTP service as its sender, even merely by upgrading. With an eligible custom-domain sender, generate its SMTP token in **Settings → All settings → IMAP/SMTP → SMTP tokens**; use `smtp.protonmail.ch` on port `587`, the selected custom-domain address for `SMTP_USER`/`EMAIL_FROM` and the token for `SMTP_PASSWORD`. Never enter the ordinary Proton account password into Render. Keep the requested Proton mailbox as the reply address.

If there is no custom domain, keep Proton for incoming contact/replies and connect a separately authorised sender. An owner-controlled iCloud mailbox can use SMTP with an Apple app-specific password; a verified-domain Resend sender is another option. Proton Mail Bridge is a desktop-client connection, not a Render-hosted mail service. The software cannot create mailbox credentials or bypass sender authentication. Save the settings and deploy, then check the mail setup and receipt with a test recipient you control.

Every successful new signup queues one generic account welcome message. There is no historical-member backfill or marketing subscription. Missing sender configuration leaves it pending; the Members view shows actual queue status. **Sent means provider acceptance, not guaranteed inbox delivery.** After correcting a sender failure, the administrator can use the failed-message retry action. It does not send a new message to historical members or resend an already accepted message.

No password, ID photo, selfie or date of birth is sent in the welcome message. It confirms account creation and directs the member to their current review status; email does not approve the application or verify email ownership. Deleting a member cancels queued jobs but cannot recall messages already in flight or sent.

## 11. Use account notifications

1. Sign in to the protected admin or staff dashboard. The **Notifications** bell and navigation item show your unread count. Open **Notifications** to see recent membership activity.
2. New membership applications, successful ID/selfie submissions or renewed eligibility applications, completed staff reviews and actual member-name changes create events. Routine sign-ins, password changes and saved-favourite changes do not create these alerts. Deployment does not manufacture alerts for earlier account history.
3. Open a notification's member or verification link to see that exact member's current record. Notification text does not include an ID image, date of birth, email address or review document.
4. Mark an item read, or choose **Mark all read** for the currently loaded event boundary. Events received after that boundary remain unread. Read status is saved in SQLite for your account and survives sign-out and restart; an administrator reading an item does not clear an individual employee's item. A retained legacy shared staff login shares its own read status.

The dashboard checks for updates about every 15 seconds while visible and when it regains focus or connection. Keep the dashboard open for in-app updates. These alerts do not require a mail sender and do not promise an email, sound, browser push or operating-system notification. A lost or revoked staff session removes private notification access.

The feed retains events for up to 30 days and at most 10,000 shared activity records. Linked events and read receipts are removed when a member is deleted. Event records store member references, event type, time and hashed source references; read receipts use a hashed staff identity. The protected feed looks up the member's current name instead of keeping copied profile details. Backups retain their separate lifecycle.

## 12. Find membership numbers and digital cards

After the required staff or administrator review is approved, members see **Verified member** on their card and the completed review panel/checklist disappears from their dashboard, including after a new sign-in. Pending or unsuccessful reviews keep their next steps available. If changing the account name requires a new review, those steps return.

Every member has a permanent, random **membership number** in the form `LC-123456`. Existing accounts receive one automatically during the database migration; new accounts receive one within signup. The number remains stable after a name change or restart. In **Members**, search using the member's name, email or membership number.

Members see their digital card on **Your account** (`/account`). It shows their name, membership number, joining date and current verification status, including a pending or required review. **Download membership card** saves a private SVG copy of those details. A download is a snapshot and does not update when the review status changes; the signed-in dashboard shows the current status. The card is an account reference, not government ID, proof of age, a completed identity check or a payment card. It does not change account eligibility or business permissions. Downloaded cards contain no email address, date of birth, ID/selfie images or passwords.

## 13. Scan a membership card

1. Sign in with an administrator or individual staff account and open **Scan member card**.
2. Choose **Start camera**, allow camera access and hold the complete barcode in the frame. Use the live HTTPS service. **Stop camera** ends capture; it also stops after a match, when the tab is hidden, or when you leave the scanner.
3. Alternatively, enter or scan the printed **Membership number** using a USB scanner and press Enter / **Find member**. **Barcode image** accepts a JPEG, PNG or WebP photo or screenshot of up to 6 MiB.
4. Read the current member name, membership number and verification status returned by the service. A copied card is an account reference, not proof of the holder's identity. **Open member record** opens the private directory; an incomplete review also has **Review application**.
5. Use **Clear result** before looking up another member. If camera access is unavailable or denied, the image and number methods remain available.

Decoding happens locally; this scanner does not upload photos, request microphone/location access, or save scan history. Only the decoded number is sent to the private lookup endpoint. Pending, rejected, changed or deleted accounts are checked against current server records rather than the status on an old card. New card downloads contain the barcode; older saved copies need to be downloaded again.

The **Search member ID** field at the top of both dashboards also opens this lookup. Enter LC- and six digits, or just the six digits. Earlier long card numbers remain aliases for the same member after the one-time format migration; the result shows the new number. New six-digit numbers stay stable and are never reissued after deletion. The database retains an unlinked reservation of previously issued numbers.

## 14. Review processed merchandise by date and staff member

1. Sign in as the administrator and open **Processed reports**. Individual staff and member sessions cannot open this report.
2. Choose the non-cannabis merchandise products to include and select **Save report products**. The selection is stored on the server. If another admin session changed it, refresh and review the new selection before saving again.
3. Apply a date range of up to 366 days. Dates and daily groups use **Africa/Johannesburg (SAST)**, including the start and end dates.
4. Review the grouped records, selected products and quantities, and recorded staff name. Only eligible completed or delivered records appear. Older records without a saved completing employee show **Not recorded**; a shared legacy login shows **Shared staff account** rather than an invented person's name.

To create a product yourself from this tab, select **Add product** under **Choose report products**. Enter its name, price in rand, unit/size and description, then select **Create draft product**. It is saved in the catalog as an Accessories draft and checked in your current report selection when space is available. Select **Save report products** to persist that selection. Creating a product preserves your other unsaved choices and does not publish it or create processed records. You can edit its photograph and publish it separately from **Products**. Up to 100 products can be selected for a report.

The product picker is restricted to the current **Accessories** category, and each historical line must also have that category. Other categories, customer details and full-order totals are excluded. Changing the report selection does not change a historical record or award rewards. New eligible completion metadata preserves the authenticated employee's name at that time; it cannot reconstruct missing historical staff names.

## 15. Confirm merchandise payment and manage member rewards

1. From an eligible processed record, choose **Record merchandise payment**. Review the server-calculated eligible merchandise amount. An already recorded receipt cannot award credit again.
2. Enter the correct member's membership number and look up the account. Confirm the member name and current number.
3. If the member wants to apply existing merchandise credit, enter an amount within both the available balance and eligible merchandise amount. The dialog shows the remaining externally paid amount.
4. Confirm that the correct member's eligible merchandise payment was actually received, then select **Record paid merchandise**. Keep any underlying receipt/payment evidence through the business's existing process; this action records an administrator's attestation, not a processor settlement.
5. The member can open **Merchandise rewards** on their own dashboard and refresh their balance, progress and recent earned/redeemed entries.

The rule is **R10 credit for each cumulative R1,000 of eligible external paid spend**. For example, R600 followed by R400 of eligible externally paid merchandise reaches the first R10 award. Discounts are allocated proportionally to eligible merchandise; delivery and other product categories do not count. Credit used on a purchase is excluded from new qualifying spend. A completed status alone creates no award, and no earlier purchases are credited automatically.

Only an administrator can confirm payment or apply credit. Report product choices do not redefine reward eligibility: all qualifying current-and-historical Accessories lines are considered by the reward calculation. Tokens are nontransferable merchandise store credit; no cash-out, transfer, cryptocurrency, payment processing or automatic refund/reversal feature is provided. A confirmation retry is idempotent, and conflicting repeat details require review instead of a second award.

Deleting a member removes that member's reward balance and ledger. Receipt references, amounts and trusted administrator confirmation remain without a member link under the business's separate retention process, so the same receipt cannot be credited to a new account. Back up the entire persistent database with the existing backup procedure; do not reset member records or change the upload-encryption key for these features.
